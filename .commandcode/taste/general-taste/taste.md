# General Taste
- Prefers deploying web apps to zero-config serverless hosting platforms (Vercel or equivalent) rather than self-managed servers. Confidence: 0.8
- Works on Windows (cmd/PowerShell, paths under `C:\Users\...\OneDrive\...`); commands and scripts should be Windows-compatible. Confidence: 0.8
- Supplies official vendor SDKs locally plus links to official docs, and expects those to be read/consulted before implementation instead of guessing APIs. Confidence: 0.7
- Gives high-level goals and leaves architecture/stack decisions to the assistant; does not micromanage implementation details. Confidence: 0.6
- Prefers to handle git commits and pushes to remote repositories themselves; the assistant should stage/edit files and then instruct the user to commit and push, rather than running `git commit` / `git push` on the user's behalf. Confidence: 0.85
- When reporting errors, often appends a hypothesis about the cause (e.g. "I think the url should be include a port"). The assistant should evaluate these hypotheses but ultimately defer to evidence from official sources/SDK code rather than acting on unverified guesses. Confidence: 0.6
- When the API call succeeds (no error code) but the UI shows empty/wrong data, expects the assistant to verify the response field names against the official SDK source rather than assuming the frontend is parsing correctly. Confidence: 0.7
- Prefers the assistant to cite official SDK/docs sources inline at the end of substantive technical answers (e.g. a "Sources:" list with links to vendor SDK code or docs). Confidence: 0.8
- When debugging third-party SDK errors (e.g. player SDK throwing a vague message), expects the assistant to read the vendor SDK's own source/docs to find the root cause (missing constructor options, wrong field types, etc.) rather than guessing or treating the SDK as a black box. Confidence: 0.8
- Flags bugs by contrasting the app's own status message against observed behavior ("it said playing, but no stream on the grid") — so treat a UI that reports success while the underlying operation did nothing as a bug in itself: count/report partial and total failures honestly (e.g. `Playing 2/4 cameras`) instead of optimistic banners, and surface the real error per item. Confidence: 0.7
- Writes short, informal, typo-heavy English bug reports ("It siad playing", "dis not support") describing symptoms rather than root causes, and expects the assistant to infer the intent and start investigating the code immediately instead of asking clarifying questions. Confidence: 0.6
- Keeps agent/tooling session artifacts out of version control — asked for `.commandcode/` to be added to `.gitignore` (and flagged that taste memory should not live in the repo), so exclude Command Code state/taste files from any repo the assistant touches. Confidence: 0.75
- Treats documentation as part of the work: expects `README.md` to be rewritten in step with the code, covering the current feature set, architecture, deploy workflow, and accumulated gotchas/troubleshooting — not left describing an older version. Confidence: 0.75
- Works through defects one at a time in a continuing session, confirming each fix with a terse verdict before moving on ("Great. It works! Now, let try to fix the PTZ control"), and expecting the previously agreed fix to be left as-is while the new symptom is traced to a specific line/mechanism rather than patched blindly. Confidence: 0.75
